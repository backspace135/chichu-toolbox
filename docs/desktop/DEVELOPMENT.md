# 桌面端开发文档

**编写日期：2026-11-09（JST）。状态：技术栈与 UI 已确认，工程尚未初始化；本文为后续实施与验收计划。**

本文覆盖 Windows、macOS 桌面端的产品边界、功能分期、工程组织、设备通信、任务与解锁流程、构建发布和验收方式。确认的技术选择见 [TECH_STACK.md](TECH_STACK.md)，视觉与交互以用户确认的 [UI_DESIGN.md](UI_DESIGN.md) 为准。

整体进度与待决策项由 [桌面端总 issue #10](https://github.com/backspace135/chichu-toolbox/issues/10) 跟踪。

## 1. 产品目标与版本边界

桌面端定位为 **一键强制解锁 Bootloader + 日常 Android 玩机工具箱**：整合已有开源方案，让用户在一个应用中连接设备、检查适配、完成受支持的解锁流程，并进行应用管理、文件传输与调试。

“一键”表示应用负责已具备自动化条件的步骤编排。手机授权、进入特定模式所需的按键与插拔、系统驱动批准等实际人工动作，在对应阶段给出引导；不能把这些动作伪装成全自动完成。

### 完成的定义

桌面总目标完成时，应该具备：两端可安装的应用、真实设备管理与任务记录、实用 ADB 工具、至少一条有完整真机证据的强解路线、清晰的设备/固件/主机支持表，以及对应构建与验证记录。仅完成外壳、mock 或候选方案扫描不算完成解锁目标。

## 2. 功能规划

### 2.1 核心基线：优先实施

以下是开发计划，不改变 UI 已确认、功能清单仍待最终确认的边界。

| 功能组 | 计划内容 | 实现与验收重点 |
| --- | --- | --- |
| 连接与设备概览 | USB ADB 发现、多设备选择、授权/offline 状态、基础设备/ROM/内核信息 | 每项来自真实设备；区分未提供、无权限、读取失败 |
| 模式与重启 | ADB、Bootloader Fastboot、Fastbootd 的实际识别与对应重启入口 | 发送重启指令不等于已到目标模式；按真实观测更新 |
| 应用管理 | 名称/包名搜索，用户/系统/已冻结筛选，详情、启动、强停、冻结/解冻、卸载、清除数据 | 操作绑定具体设备与用户；恢复当前用户卸载的系统包另行核实能力 |
| APK 安装与提取 | 单 APK、拆分 APK 安装，提取 base 与 split 文件 | 拆分安装作为完整会话处理；提取结果保留所有部分与版本信息 |
| 文件传输 | 可访问目录浏览、电脑与手机双向传输、进度与结果 | 使用流式传输；大文件不进入前端内存；文件名和路径支持中文、空格 |
| 截图 | 设备截图、预览、用户选择位置保存 | 保存失败可定位；截图不使用 mock 插画代替 |
| Shell 与日志 | xterm.js 交互式设备 Shell、会话重开、任务输出与导出 | 不是简单的单次命令输入框；会话与页面生命周期分离 |
| 强解工作流 | 识别、精确适配、相关备份、分步执行、结果验证 | 先固定一条可复现路线；成功必须由最终设备状态证明 |
| 设置与关于 | 深浅色、紧凑模式、实际存在的连接与记录偏好、工具版本与许可 | 每个设置都有实际使用方，不能只有无效开关 |

应用名、图标、占用空间等信息不一定都可由同一条 ADB 命令读取。实施时按实际数据来源完成；读取不到的字段不填演示值。占用空间必须明确是 APK 大小还是应用总占用，不能混用。

### 2.2 扩展候选：保留方向，按需求排期

gjgjxweb 的下列能力继续作为后续候选：无线调试配对/连接、分辨率和 DPI、字体与动画倍率、自动锁屏时间、状态栏/沉浸设置、电池记录与 CSV、批量应用方案、命令收藏与脚本。

这些能力使用同一设备与任务底座。ROM 特有设置逐项验证，修改时记录原值、修改值和结果；不能提供不相关设置捆绑的“一键优化”。电池模拟与真实电池读数必须区分。

BAT 子集解释器不是通用 Windows 命令执行环境；是否兼容其脚本单独决定。投屏、完整刷机与救砖、官方账号解锁属于另外的范围，不因工具依赖具备相关命令而自动进入首版。

### 2.3 与 Android 客户端的关系

日常 ADB 管理不依赖安装 Android 客户端。后续如果接入安装/启动内置权限服务、诊断联动等能力，单独确定接口与对应里程碑；不能把桌面计划反向扩大为 Android v0.1.0 的交付内容。

## 3. UI 实现要求

侧栏保持「设备概览 → 解锁 Bootloader → 应用管理 → 文件传输 → 终端与日志」，设置位于底部。顶部设备上下文和任务记录入口贯穿页面。

- `MantineProvider` 统一主题、颜色、控件尺寸与默认值；不在业务页重新定义按钮和表格风格。
- 业务布局使用 CSS Modules。标准控件优先 Mantine，不把 mock 的全局 CSS 和单组件结构当成正式工程架构。
- 前端只展示状态和发起操作，连接与长任务的权威状态在 Rust 中维护。
- 设备详情、安装、应用详情使用弹窗；完整任务记录使用抽屉。
- 当前页搜索、筛选、选择等局部状态由页面维护；共享当前设备与任务摘要使用小范围 Context/reducer，在确有调用需求后再决定额外状态库。
- 高级表格在应用管理实施时确定。少量数据先使用 Mantine Table；实测数量或交互需要虚拟化时再引入，不预先堆叠依赖。
- 正式界面不包含示例设备、预设 Shell 响应、演示完成按钮或占位成功状态。

视觉细节、令牌、缩放、键盘与变更流程见 [UI 规范](UI_DESIGN.md)。mock 的 390px 检查只是响应式参考，正式窗口最小尺寸另行确定。

## 4. 工程布局与依赖管理

共享工程位于 `apps/desktop/`。下列是初始化后的目标布局，当前只有入口 README，尚不代表目录或脚本已经存在。

```text
apps/desktop/
  package.json / package-lock.json
  src/
    app/                     应用框架、导航与主题
    features/
      devices/               概览与设备选择
      unlock/                适配与解锁流程
      apps/                  应用列表与操作
      files/                 文件与截图
      terminal/              Shell 与日志
      settings/              设置与关于
    components/              实际复用的业务组件
    bridge/                  Tauri 命令、类型与通道封装
  src-tauri/
    Cargo.toml / Cargo.lock
    tauri.conf.json
    capabilities/            窗口可用能力
    src/
      commands/              Tauri 边界与输入校验
      devices/               设备发现、身份与状态
      adb/                   ADB 工具调用与解析
      fastboot/              Fastboot 调用与解析
      tasks/                 任务生命周期、日志与产物
      unlock/                已采用方案的实际编排
      terminal/              交互会话
      settings/              配置文件
    binaries/                按主机平台准备的工具产物
    resources/               需要随包分发的资源与声明
  scripts/                   工具打包、验证与平台脚本
  tests/                     IPC/任务/打包的必要测试
docs/desktop/
  TECH_STACK.md / UI_DESIGN.md / DEVELOPMENT.md
  MANTINE_MOCK.md
  后续各里程碑验证记录
```

- 前端依赖精确版本和 lockfile 固定；Rust 固定工具链与 Cargo.lock，CI 使用相同版本。
- Node、Rust、Tauri CLI 和构建插件版本在 D1 固定；Mantine 以确认基准 9.8.0 起步，升级需重新检查组件与 WebView 兼容性。
- 先按实际功能组织 Rust 模块，不提前拆多 crate、插件系统、通用工作流 DSL 或跨端共享框架。
- npm 是本次预览使用的包管理工具，正式工程沿用 npm，避免在同一工程维护多种 lockfile。
- 构建、缓存、工具下载与产物保留在工程忽略目录中，不提交 node_modules、target、dist 或签名材料。

## 5. 分层与通信

```text
React 页面与共享组件
       │ 明确的业务命令 / 状态查询
       ▼
Tauri command 边界
       │ 参数校验、设备/任务标识、结构化错误
       ▼
Rust 设备与任务服务
       │ 外部进程、流、结果解析、文件与日志
       ├── adb
       ├── fastboot
       └── 选定的解锁工具 sidecar
       │
       └── 状态快照 + 按任务/会话划分的 Channels → 前端
```

### 5.1 命令边界

命令按业务定义，例如查询设备、读取应用列表、创建安装/传输任务、开始适配检查、打开 Shell 会话；不向普通业务页面暴露“传入任意电脑 shell 字符串”的接口。

结构化参数经 Tauri 边界校验后进入内部模块，不逐层重复校验。命令参数列表直接传给程序，电脑端不经过 `cmd /c` 或 `sh -c` 拼接；传入 Android shell 的包名、路径和文本按其真实边界处理转义。

Shell 功能允许用户明确输入设备端命令，其授权语义与应用的普通按钮操作保持独立，不让导入脚本顺带执行电脑上的程序。

### 5.2 快照与事件

- 设备列表、任务列表和终端会话由 Rust 持有，页面重开后可查询当前快照。
- 长输出与进度使用按任务或会话划分的 Tauri Channel；低频通知使用事件。
- 事件包含任务 ID、设备 ID、阶段和顺序标识，前端不能把旧设备的异步结果写进新设备页面。
- 订阅和初始快照要建立明确顺序，避免两者间丢状态；实现时选择一个可验证的顺序方案，不引入第二套消息中间件。
- 文件传输、截图落盘、镜像/包处理在原生层完成；前端只拿展示所需的数据、文件元信息和进度。

### 5.3 错误

在外部进程、USB、文件、系统对话框和用户输入等真实边界处理可发生的错误。错误至少保留操作、工具、退出码及可定位的输出或具体原因，返回给对应操作区域和任务记录。

不以空列表掩盖读取失败，不用默认值假装连接正常。内部不变量失败直接暴露；没有证据不加自动重试、任意超时、候选方案轮试或兼容分支。取消与失败单独建模。

## 6. 设备模型与连接

### 6.1 设备信息

设备记录按实际来源维护：ADB 序列号/transport、型号、产品代号、完整构建、Android/API、内核、主机观察到的 USB 信息，以及当前可观测的模式。某字段不存在时记录“未提供”；解析或权限错误保留各自状态。

连接状态和能力分开：`unauthorized` 不是 offline，ADB 在线不等于 Root，知道设备代号不等于方案受支持。Bootloader 状态应保留来源、读取时间与结果；无法在当前模式验证时不能沿用旧值冒充当前已确认。

### 6.2 ADB

- 固定并记录使用的 ADB 版本与路径，先使用现有 ADB server 协议和工具能力，不自行重写 USB ADB。
- 使用 `track-devices` 等实际可用接口获取设备变化。每个操作指定目标序列号或 transport，禁止依赖“第一台设备”。
- 明确 ADB server 的版本和归属；发生不兼容或占用时给出实际原因，不自动结束用户其他工具或不加说明地反复 `kill-server`。
- 无线配对、mDNS 与 TCP 连接是后续能力，发现、配对、连接、Shell 可用分别验证。

### 6.3 Fastboot 与跨模式身份

- 原生 Fastboot 输出可能写入 stderr；有 stderr 不等于失败，按退出状态与协议内容解析。
- Bootloader Fastboot 与 Fastbootd 依真实变量识别，不能仅凭按钮名称判定。
- 模式切换后序列号、接口和 USB 地址可能改变。使用实际观测建立关联；无法唯一关联时让用户选择，不能拿另一台设备继续原任务。
- USB 枚举、ADB 与 Fastboot 信息按已接入功能逐步实现；没有 EDL/BROM 实现时，不凭 USB 名称宣称能够解锁该模式的设备。

## 7. 任务、日志与产物

### 7.1 生命周期

```text
等待开始 → 准备中 → 执行中 ↔ 等待用户 / 等待设备
                         ↓
                       验证中
                         ↓
               成功 / 失败 / 已取消
```

任务保留 ID、固定目标设备、操作类型、阶段、可取消性、进度、时间、日志和文件产物。进度只有在总量可知时显示百分比；工具只有阶段输出时使用阶段进度。

- 同一设备上的冲突操作在原生层排他，例如解锁期间不能同时执行重启或安装。读操作并发按工具实际能力决定，不预建复杂调度器。
- 用户切换顶部设备只改变界面上下文，不改变已创建任务的目标。
- 停止按钮仅在工具和阶段允许时提供。终止电脑进程不等于设备操作已回退；需要后续验证时显示未验证状态。
- 关闭窗口时，对活跃任务说明具体状态并处理实际生命周期；不能静默关闭、留下无人管理的写入进程或伪造取消成功。
- 应用异常退出后，保留任务记录并标记中断。重新打开不自动恢复设备写入，先重新读取设备状态。

### 7.2 日志与文件

- 每个任务独立保存结构化摘要与文本输出，设置和记录使用本地文件，初期不引入数据库。
- 日志保留 stdout/stderr 来源、退出码和工具版本。手机上的时间与主机接收时间区分，展示时间转换为 JST；原始值可保留用于定位。
- 配对码、授权秘密不写入日志。导出诊断时提供明确内容说明与设备标识处理，不假设所有序列号都可公开。
- 备份、截图、提取的 APK 等产物记录设备与任务关联、文件大小、必要的校验值及保存位置。
- 普通产物使用用户选择的目的路径；设置和日志使用平台应用数据目录，开发及 Windows 测试机上的缓存仍遵守仓库访问限制。

## 8. 日常工具实现要点

### 应用

列表读取与变更操作分离。当前用户 ID、包名和状态有明确来源；“恢复系统应用”仅恢复仍存在且能恢复到该用户的包，不承诺重新下载已移除的系统文件。

拆分安装按会话创建、写入、提交和结果检查处理，失败后清理实际创建的安装会话和临时文件。批量操作逐项记录结果，不能部分失败却统一显示完成。APK 提取保留 base/split 组合，不把单独 base.apk 当作完整可安装备份。

### 文件与截图

目录、传输和保存校验在文件边界处理；拒绝或读取失败不返回空目录。根据任务取消能力处理实际资源释放，保存失败不删除设备源文件。截图可以直接流式读取到本地，避免无必要的设备临时文件。

### 交互 Shell

xterm.js 只负责呈现与键盘输入，Rust 负责会话。实施时验证设备 PTY、ANSI、Ctrl+C、工作目录保持、窗口尺寸和退出状态。Windows 如采用主机 PTY，需要验证 ConPTY；若直接实现设备 Shell 流，则按其协议验证，不能把普通进程管道误当成完整终端。

Logcat 筛选作为后续调试增强；任务日志是核心基线，两者不可混称。会话结束、设备断开和工具错误分别显示。

## 9. 首个解锁方案

### 9.1 候选评估

| 候选 | 定位 | 当前接入判断 |
| --- | --- | --- |
| [mtkclient](https://github.com/bkerler/mtkclient) | Python / USB 的 MTK 通信与维护实现 | 首个优先验证的引擎，需精确测试机与双平台验证 |
| [Jz8Root 研究](https://github.com/Jz8Root/xiaomi-hyperos-bootloader-unlock) | LK 构建与 RPMB 等设备相关研究 | 用于补充适配证据；复杂构建相关路线在基础路线后另立验证 |
| [xiaomi_ubl](https://github.com/18xjul08/xiaomi_ubl) | 高通设备相关资料、资源与流程 | 资源与设备清单不能替代完整可复现实现，暂不作为已确认首个目标 |
| [MiUnlockTool](https://github.com/MiForge/MiUnlockTool) | 官方账号授权路线的第三方客户端 | 不属于强解，若采用则单独说明与排期 |

目前没有经本项目验证的桌面强解设备。已有 Xiaomi 15 不能作为 MTK 路线测试机；候选仓库提到 Xiaomi 15 也不等于该机当前固件受支持。

### 9.2 接入前必须形成的实际证据

先确定可取得的测试设备、子型号、SoC、完整 ROM/LK 等方案需要的构建身份、当前锁状态与可用主机。形成一个精确组合的验证记录，不能从“同 SoC”“同代号”推断全部版本支持。

首个方案按实际路径固定上游提交、资源来源、所需 Python/原生依赖、可用主机与人工步骤。基础 seccfg 路线优先验证；如果选中设备实际需要其他路线，应重新明确对应范围，而不是无提示切换。

### 9.3 流程与结果

```text
读取设备与环境
   → 匹配具体方案与证据
   → 准备该方案实际需要的备份和资源
   → 执行阶段与人工动作引导
   → 重新建立目标设备连接
   → 按方案验证最终 Bootloader 状态
   → 保存结果与相关文件
```

解锁记录区分“检查通过”“步骤执行完成”“最终状态已验证”。工具正常退出或打印成功不能直接等同解锁成功；返回设备后仍需验证时显示待验证。不支持、证据不足或主机依赖不可用时明确说明，不自动轮试其他候选。

本阶段仅实现首个真实采用方案的编排，不创建无人使用的通用脚本引擎、在线插件市场或任意固件下载器。

## 10. 工具打包与双平台约束

### 共通要求

- 用户安装应用后不应为常规使用自行安装 Node、Rust、Python、pip 或 Homebrew；所需运行环境与工具按实际功能随包提供。
- sidecar 按目标平台构建、固定版本和校验值，Tauri 包包含正确的对应产物。
- 大型镜像与机型资源不在没有首个实际需求时全部内置；资源的交付方式和来源随选定方案确定。
- ADB/Fastboot、Python 依赖及采用上游的源码、许可与资源分发要求逐项核对。gjgjxweb 为 GPL-3.0-only；Jz8Root 候选为 AGPL-3.0；最终项目许可根据实际复用关系确定，不能把进程分离当作自动免除许可义务。

### Windows

- 初期按 `x86_64-pc-windows-msvc` 准备主程序与工具；明确 WebView2 安装或引导方式。
- 驱动依模式与工具不同：ADB/Fastboot 驱动与 MTK 低层 USB 驱动分别验证。
- 正常业务以普通用户运行。确有驱动安装或系统操作需要提升时，按该操作处理，不让整个应用默认管理员运行。
- 处理带空格/中文路径、控制台窗口隐藏、进程树与取消；测试安装包在无开发工具环境下启动。
- 使用 `g16win` 时仅访问当前项目 `D:\project\chichu-toolbox` 与允许的开发工具链。缓存、TMP/TEMP 和构建产物留在项目内；非工具链驱动/系统修改需先向用户确认。

### macOS Apple Silicon

- 主程序 target 为 `aarch64-apple-darwin`，可执行工具与动态库具有原生 arm64 支持；不提供 Intel-only 依赖或以 Rosetta 作为前提。
- 在所定最低 macOS 上构建/验证对应 Python 与原生库的部署兼容性，不能只在新系统开发机上启动一次即宣称兼容。
- 分发时核对 sidecar 的可执行位、动态库查找、签名与公证配置，并在脱离开发环境后验证。
- macFUSE 等只有具体功能确实依赖时才纳入，不能从上游完整安装说明推导所有解锁功能都必须安装。
- 采用 WKWebView 实测，不能以 Chromium mock 替代；系统 USB、文件和局域网授权按实际使用需求处理。

## 11. 最低版本决策方法

在 D0 中确认候选，在 D1 记录打包验证，在采用解锁工具后再次核对依赖交集。

| 维度 | 决策依据 |
| --- | --- |
| 主程序 | Tauri/Rust 实际版本及目标平台要求 |
| UI | Mantine 所用 CSS/浏览器能力在最低 WebView 上可用 |
| ADB/Fastboot | 固定版本可执行文件在目标系统运行与设备通信结果 |
| Python/USB | 冻结后的运行时、原生库和驱动能正常加载与通信 |
| 发布 | 安装器、签名、公证与升级配置 |

框架理论下限、开发机要求和完整应用支持基线分别记录。Windows 10 22H2 的 WebView2 维护信息可作为评估依据，不能代替应用测试；Apple Silicon 也不能自动确定最低 macOS。当前不把讨论候选写进成品支持声明。

### 12.1 D1 建立的命令契约

下列为**计划在工程初始化时实现的命令**，当前尚不能在占位工程执行。工作目录均为 `apps/desktop/`，Rust 命令在 `src-tauri/`。

| 用途 | 计划命令 |

### 12.2 测试分层

- **纯逻辑**：真实工具输出解析、设备身份匹配、方案选择、任务转换和取消语义。保留有代表性的正常/失败输出，不为不存在的内部状态堆用例。
- **进程与文件集成**：用受控测试进程验证输出、退出与取消；临时目录验证大文件、保存失败、清理和包含中文/空格的路径。
- **前端与 IPC**：真实业务状态的呈现、旧设备结果不污染新页面、搜索/选择与错误反馈。mock 仅为测试输入，不能进入正式运行状态。
- **真机**：授权、多设备、断连、模式变化、安装提取、文件传输、Shell 和选定解锁路径的最终状态。
- **正式窗口视觉**：Windows WebView2、macOS WKWebView 的深浅色、缩放、窄窗口、焦点、弹窗、表格、终端与长日志。
- **发布包**：脱离开发环境验证安装/启动、工具版本、依赖加载和签名配置；构建成功不等于发布包可用。

### 12.3 CI

- Windows x64 与 macOS arm64 独立 job，共享版本锁定和检查流程，产物按平台命名。
- 每次相关改动执行前端检查/必要测试、Rust 格式/静态检查/测试与打包。
- 工具打包任务验证架构、版本、文件清单和声明；主包构建可使用提前验证的固定工具产物。
- 真机解锁不在普通 GitHub Actions 上自动执行，结果来自专门记录的测试设备与主机。
- 本地仅启动前端/mock 开发服务；结束前停止。该工程不需要数据库或其他常驻数据服务。

## 13. 实施里程碑

里程碑编号仅用于桌面端，不与 Android 的 M1–M4 混用。

| 阶段 | 交付物 | 关闭条件 |
| --- | --- | --- |
| D0 决策与可行性 | 系统基线、首版清单、测试设备、首个方案及上游快照 | 待决策项有明确结论；方案具备可复现输入和测试条件 |
| D1 工程与 UI 骨架 | Tauri/React/Rust 工程、Mantine 主题、六页导航、两端 CI | 两端正式窗口与安装包启动；无 mock 数据混入 |
| D2 设备与任务底座 | ADB 发现/选择、Fastboot 识别、身份/模式、进程、日志和任务抽屉 | 多设备/断连/授权/模式切换与任务目标准确 |
| D3 应用管理 | 列表、筛选、详情、启停、冻结/卸载、安装和提取 | 正常与实际权限/安装失败均验证，拆分包完整 |
| D4 文件与截图 | 目录、传输、保存、进度、产物 | 大文件与中文路径可用，断连/取消/保存失败可定位 |
| D5 交互终端 | xterm.js、设备会话、输入输出、任务日志导出 | Ctrl+C、尺寸变化、切页、断连和退出验证 |
| D6 首个强解闭环 | 单条已固定方案、精确适配、必要备份、引导、执行与结果验证 | 首个承诺方案在两种目标主机上分别形成真机证据；固件与结果明确，支持表无外推 |
| D7 双平台发布验收 | 签名/分发配置、安装包、运行说明、许可清单与回归记录 | 目标系统/架构正式窗口、日常工具与强解支持范围验收通过 |

默认顺序为 **D0 → D1 → D2 → D3/D4/D5 → D6 → D7**。解锁工具的独立可行性验证可在 D0 后推进，UI 执行接入依赖 D2；无需等待所有日常工具页面完成才调查底层解锁依赖。D7 汇总实际承诺范围，不能用“稍后增加”关闭缺失的核心解锁目标。

## 14. 总体验收标准

1. Windows 与 Apple Silicon macOS 均有可安装、无需用户开发环境即可运行的应用。
2. 正式 Tauri 窗口对齐已确认 Mantine UI，深浅色和关键交互分别在两端记录证据。
3. 所有操作绑定正确设备；未授权、offline、多设备、模式切换与断连不显示虚假成功。
4. 应用、文件、截图与 Shell 基线功能使用真实数据，实际失败保留原因与任务记录。
5. 切页/切设备不改变运行任务目标，进度和取消能力符合真实工具语义。
6. 至少一条强解路线在 Windows 与 Apple Silicon macOS 上分别有精确设备/固件/上游/主机证据及最终状态验证。若某平台不可行，返回方案决策，不静默将其降为仅日常工具可用；其他扩展方案按各自证据记录主机差异。
7. 成品最低系统版本、各功能主机差异、设备支持表、工具与资源版本及许可明确。
8. mock 的示例值、预设输出、模拟按钮和预览标识不进入正式客户端。
