# 禁止过度防御化编程

本 skill 优先于其他编码习惯与风格偏好。与其冲突时，以本 skill 为准；只有用户在当前对话中的明确指示可以覆盖它。

## 核心原则

**每一行防御代码都必须能说出：哪个真实输入或真实环境会触发它，触发后用户看到什么。说不出来，就删掉。**

失败应当尽早、响亮、可定位。被吞掉的异常、悄悄返回的空列表、无人知晓的默认值，比崩溃更难排查，也会让界面显示虚假状态，违反“原生界面使用真实设备与服务数据”。

## 只在真实边界防御

真实边界（允许校验和错误处理）：

- 外部进程与 IPC：Shizuku Binder、ADB 连接与配对、`sh`/`su` 输出、KernelSU 接口。
- 设备与系统：`PackageManager`、系统属性、`/proc`、`/sys`、内核配置文件、网络服务发现。
- 用户输入、文件读写、权限被拒、Activity 无法解析等系统可能拒绝的调用。
- 安全相关：Shell 授权、调用方身份、命令拼接（宁可拒绝，不可放行）。

内部代码（不做重复防御）：

- 自己模块构造并传入的数据、`sealed`/`enum` 已穷举的状态、类型系统已保证非空的值。
- 已在边界校验过的值，进入内部后不再逐层重复校验。
- `minSdk = 31` 以下的系统行为、不存在的旧数据格式、没有调用方的“未来扩展”。

## 禁止的写法

| 禁止 | 改为 |
| --- | --- |
| `runCatching { … }.getOrNull()` / `getOrDefault(...)` 吞掉所有异常 | 让异常抛出；或只捕获具体异常类型，并转换成明确的用户可见状态 |
| `catch (e: Exception)` / `catch (e: Throwable)` 后什么都不做或只打日志 | 捕获具体类型（`IOException`、`NameNotFoundException`、`SecurityException`…）并处理；处理不了就不捕获 |
| 吞掉 `CancellationException` | 协程中宽捕获前必须先 `catch (e: CancellationException) { throw e }`（沿用仓库现有写法） |
| 类型本来非空，却声明成可空“以防万一”，再到处 `?.`、`?: return`、`orEmpty()` | 用非空类型；真可能缺失的值在边界处一次性决定语义 |
| 用 `!!` 代替思考 | 不变量用 `checkNotNull(x) { "原因" }` / `requireNotNull`，写清违反时的原因 |
| 对 `sealed`/`enum` 的 `when` 加 `else -> {}` | 穷举所有分支，让新增状态在编译期暴露 |
| 不可能发生的分支返回默认值 | `error("…")` / `check(…)`，让 bug 当场暴露 |
| 没有失败证据就加重试、超时、延迟、轮询、降级路径 | 先拿到真实失败场景（日志、设备、协议规定），再加，并在代码旁写明场景 |
| 无人使用的参数、配置项、feature flag、兼容层、抽象接口 | 只写当前调用方需要的；需求出现时再加 |
| 调用前重复检查被调用方已经检查过的条件 | 信任被调用方的契约，只在一处检查 |
| 防御性拷贝、`isNotEmpty()` 再 `forEach`、`size > 0` 再取首个仍然判空 | 直接写；Kotlin 集合操作本身已安全 |
| 发生错误时 UI 显示“正常”“未知”或空内容，掩盖失败 | 显示真实错误状态与可操作的下一步（参照 `docs/android/UI_DESIGN.md` 的状态规范） |
| 测试里为不可能分支写用例 | 测真实边界与真实失败路径 |

## 允许并且应该做的防御

这些不是“过度防御”，必须保留：

- 资源释放：`use {}`、`finally` 中关闭 socket、进程和流；关闭时出现的异常可以忽略（例如 `runCatching { socket.close() }`）。
- 协程取消：传播 `CancellationException`；对外部调用设置**有依据**的超时。
- 系统明确会拒绝的调用：`startActivity` 可能抛 `ActivityNotFoundException`，权限可能被拒，`getApplicationInfo` 可能抛 `NameNotFoundException`。捕获**那个具体异常**，并给用户明确反馈。
- 解析外部文本（内核配置、shell 输出、ADB 报文）时校验格式，格式不符就报错，不要猜测补全。
- 安全边界上的拒绝优先：授权或身份不确定时一律拒绝。

## 改动范围

- 只改任务要求的代码。不要顺手给无关代码“加固”，比如加 try/catch、空值判断或日志。
- 不改上游代码：`third_party/`、`apps/android/core/shizuku/src/main/java/moe/shizuku/` 保持上游原样，除非任务明确要求。
- 发现现有代码过度防御时，任务范围内的直接改掉；范围外的列在汇报里，不擅自扩大改动。

## 提交前自检

对本次 diff 中每一个 `try`/`catch`、`runCatching`、`?.`、`?:`、`if (x == null)`、`else ->`、默认值、重试、超时逐一回答：

1. 触发它的具体输入或环境是什么？（必须能点名，例如“用户未开启无线调试时 mDNS 发现返回空”）
2. 这个场景在 `minSdk 31+`、本仓库真实调用链中会发生吗？
3. 触发后用户或日志能看到什么？是否掩盖了真实失败？

任何一条答不上来，删除该防御代码。汇报时说明删除或保留了哪些防御，保留的理由是什么。
